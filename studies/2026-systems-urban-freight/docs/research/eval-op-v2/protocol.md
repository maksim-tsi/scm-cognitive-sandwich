# Prospective protocol: EVAL-OP-V2 candidate

**Precursor notice:** The proposed operational-context ablation and updated execution plan are in [revision-1/protocol.md](revision-1/protocol.md). This document remains a historical description of the first 16-case candidate, not the R1 protocol.

**Status: candidate, not researcher-approved and not scientifically frozen.** One substantive researcher approval must cover the scenarios, assumptions, references, profile conditions, budget and any known limitations before a new immutable pre-inference freeze and collection. Nothing here authorizes model inference. Results from a modified candidate require a fresh version, complete offline qualification and new approval before collection; no editing after observing scientific outputs.

## Research questions and conditions

Primary: under the same stipulated operational world and text-only evidence, how often does each provider produce a completed, source-supported, computationally feasible decision or a justified insufficiency decision? Secondary: where do evidence authority, completeness, physical feasibility, correct state transition and response format fail; and does I3 change admission or utility relative to I2 for the *same* terminal proposal? D-INT is a deterministic, non-model reference comparator with the same controller, public packet, tool/question channels and limits; it is not independent evidence about real retailers.

One trajectory per case per provider, with 16 cases, four model routes and D-INT. Each normalized public packet includes the same scenario text, synthetic numeric routing inputs, dated textual visual observations, source catalog, channels and instructions. No Street View images are sent. Private references/solution labels never enter the model packet. A synthetic source's `verified` field means eligible within the simulated world, not authenticated outside it. The common task conditions remain at most three atomic questions, three tool attempts and seven model responses, with the established controller, schema, tools, evaluator and I2/I3. Provider-specific history and serialization remain part of treatment conditions.

## Decision metrics and denominators

The primary numerator is `independent_outcome_correct` from the existing evaluator (supported UPDATE/RETAIN with feasible route, correctly supported INFEASIBLE, or justified INSUFFICIENT after available channels are exhausted). Denominator is all 16 assigned cases per provider, including failed, invalid, incomplete and unattempted cases; report each disposition separately and do not replace or drop them. Also report complete-trajectory performance separately with its own denominator. The evaluator does not assign a separate correct positive score to a terminal CLARIFY that defers an available question; report `deferred_clarify` as a secondary process measure, not a completed success.

For supported decisions, report evidence-grounding errors (wrong issuer, scope, expiry, conflict, missing acquisition or nonliteral source IDs), decision/state-transition errors, and physical route errors against reference inputs. Flag unsupported numeric commitments as numeric actions without correct source grounding and report whether each gate admitted them. For insufficiency, report justified refusals, unnecessary refusals, missing-slot errors and availability of permissible clarification. Report component counts with explicit eligible denominators; categories may overlap. A computational feasible plan is not proof of real-world access. I2/I3 metrics are paired evaluations of exactly the same original terminal proposal, verified by hash; report useful admissions, unsupported admissions, additional I3 rejections, and correct proposals rejected, with failure/abstention status explicitly tabulated. Do not call a gate rejection proof that a real accident was prevented.

Report counts and case IDs, paired case-level differences and descriptive proportions; no general ranking, independent-sample significance or causal model/gate superiority from a small shared, purpose-built cohort. Cases share POIs and mechanisms. D-INT uses the existing deterministic source and route machinery and can share design assumptions with references; independent route enumeration is a cross-check, not a fully independent annotation.

## Serving profiles

- Qwen: `qwen3.8-27b-ud-q4_k_m`, local qualified JSON-only profile, temperature 0, seed 20261027, thinking disabled, max 2048 output tokens, historical tokenizer/context guard.
- DeepSeek: `deepseek-flash`, JSON-only, temperature 0, thinking disabled, max 2048 output tokens; explicitly record returned model/fingerprint and any drift. Alias versions may change.
- Mistral: `mistral-small-2603`, `native-structured-no-unique-v1` wire schema, temperature 0, seed 20261027, no reasoning, max 2048 output tokens; canonical local validation remains decisive. At least 15 seconds between completed requests.
- Luna: `gpt-6-luna`, Responses `json_object`, reasoning `none`, temperature 0, `store=false`, max 2048 output tokens, preserved original output phases, only a unique final-answer action executed. Minimum one second between completions when actual rate limits permit.

Profiles are not interchangeable: native wire schemas, history, tokenizer and provider behavior can change outputs. Record model alias/snapshot where exposed, profile, input schema, exact prompts, context, public data hashes, response, usage, timing and all failures. Provider differences and serving-profile effects cannot be separated in this observational design.

## Prospective execution boundary

After researcher approval of an exact canonical cohort hash, create a review receipt with `experiment`, `researcher_approved`, `cohort_canonical_sha256`, `manifest_sha256`, `budgets_usd` for each of qwen/deepseek/mistral/openai, and `max_hours`. Store receipt and each fresh run in private research storage. Preflight account/model availability and rate limits under a separately authorized procedure; this document does not authorize even a paid smoke. Set credentials in the named environment variables documented in `execution.md`, without writing them into repository, process arguments, messages or captures. Then use `python -m tools.eval_op_v2.collection --live --authorization RECEIPT --scenarios research/eval-op-v2/scenarios.json --output NEW_PRIVATE_DIRECTORY`. The collector checks the approved manifest hash, local source hashes, canonical cohort hash and ordered IDs before creating its run, rotates model order by case, uses separate durable journals and never retries/replaces trajectories. It requires a fresh output path. D-INT is collected without network.

Global STOP for unknown delivery, HTTP error including 429, integrity or source/capture mismatch, provider/profile drift that existing adapters reject, budget exhaustion, unexpected response envelope, prompt guard or wall-clock expiry. Model content/action-schema failures are recorded as that case's failures and collection continues. Leave unattempted remaining assignments explicit. No response repair, test-conditioned prompt or serving setting changes. Preserve original requests, Responses output items/phases, usage, timestamps, journals, errors, source/receipt hashes and all incomplete cases. A preflight confirms actual billing, available funds, account limits and current rates; ceilings are reservations, not actual invoicing guarantees.
